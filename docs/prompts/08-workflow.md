# Stage 8 — Workflow

Deck anchor: `WORKFLOW` (explicit orchestration with Microsoft.Agents.AI.Workflows).

## Goal

Add `DemoStage.Workflow`: remediation becomes an **explicit, code-built workflow** — validate,
policy, an operator-approval gate when policy demands one, execute, verify. After seven stages of
increasingly capable *emergent* model behavior, this beat shows the other half of agentic
systems: **deterministic orchestration with visible steps and branching**, where the graph is
data — it renders its own diagram.

## Scope

- **`WORKFLOW`** (`RemediationWorkflowService` in OperationsAgent.Api) — the slide-verbatim
  shape, built fresh per run so the armed breakpoint pauses right before the builder:
  `new WorkflowBuilder(validate).AddEdge(validate, policy)
  .AddEdge<RemediationPlan>(policy, approval, plan => plan is { RequiresApproval: true })
  .AddEdge<RemediationPlan>(policy, execute, ...).AddEdge(approval, execute)
  .AddEdge(execute, verify).WithOutputFrom(verify).Build()`, run through
  `InProcessExecution.RunStreamingAsync` with the event stream
  (`ExecutorInvoked/Completed/Failed`, `WorkflowOutputEvent`) projected into a live step
  timeline.
- **Five executors** (`RemediationWorkflow.cs`): validate reads the authoritative twin; policy
  decides `ActionRequired` (reported ≠ scheduled) and `RequiresApproval` (clearing a manual
  override needs a human — one put it there); approval parks in the same `PendingApprovalStore`
  the MRTR stage introduced, so the Command Center's existing prompt panel serves both; execute
  restores through a dedicated `IEnergyCommandGateway` (the only place a workflow command can
  originate); verify **re-reads** the twin and returns the outcome — success is checked, not
  assumed.
- **Definition endpoint**: `GET /api/operations-agent/remediation/definition` returns the
  Mermaid diagram generated by `WorkflowVisualizer.ToMermaidString` from the executing graph (no
  drift by construction) plus the equivalent declarative YAML
  (`workflows/restore-remediation.yaml`) — displayed, not executed. `POST /remediation` starts a
  run; `GET /remediation/runs/{id}` streams its steps. All three are 409-gated below the
  Workflow stage.
- **Command Center panel**: a **Run remediation workflow** button, a live step timeline
  (running/completed/failed per node), the approval prompt (reused), and a definition card with
  **Graph (generated)** / **Declarative YAML** tabs. Mermaid is vendored locally
  (`wwwroot/lib/mermaid`); nothing loads from a CDN on stage.

## Lecture beat

1. At the Workflow stage, open the definition card: the diagram was generated *from the code
   that runs* — point at the two policy branches.
2. Arm `WORKFLOW` in DemoControl, click **Run remediation workflow**: the debugger lands at the
   builder; step the slide-shaped graph construction, then continue.
3. The timeline fills node by node; at `approval` it pauses — the same operator prompt as the
   MRTR stage, now raised by an orchestration node instead of a paused tool. **Deny** first:
   execute reports the decline, verify reports the override still standing.
4. Run again, **approve**: execute restores through the Energy Hub, verify re-reads and
   confirms, the map updates.
5. Contrast: MRTR was a *tool* pausing mid-call; the workflow is *structure* — the pause is a
   node you can see in the diagram. Same human, different control point. Declarative YAML +
   Foundry hosting of workflows arrive in the Hosting stage.

## Verification

- Deterministic tests drive the real graph through the real engine with only the Energy Hub
  gateways faked: approve executes with the caller's correlation, deny leaves state untouched,
  no-override anomalies skip the approval gate, in-schedule state is a no-op, and the rendered
  definition names every node.
- The full flow (deny, then approve, with the SmartPole confirming) is verified live against the
  running stack.
