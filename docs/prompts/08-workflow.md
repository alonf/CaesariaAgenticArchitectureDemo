# Stage 8 — Workflow

Deck anchor: `WORKFLOW` (explicit orchestration with Microsoft.Agents.AI.Workflows).

## Goal

Add `DemoStage.Workflow`: remediation becomes an **explicit, code-built workflow** — validate,
policy, an operator-approval gate when policy demands one, execute, verify, a maintenance work
item when the correction did not hold, complete. After seven stages of increasingly capable
*emergent* model behavior, this beat shows the other half of agentic systems: **deterministic
orchestration with visible steps and branching**, where the graph is data — it renders its own
diagram.

From this stage the agent **no longer performs the write**. It requests the operation
(`start_restore_lighting_operation`) and the workflow owns validation, policy, approval,
execution, and verification. The direct `restore_scheduled_mode` MCP tool exists in exactly one
stage window — InteractiveInput up to Workflow — and is withdrawn here.

## Scope

- **`WORKFLOW`** (`RemediationWorkflowService` in OperationsAgent.Api) — the slide-verbatim
  builder, built fresh per run so the armed breakpoint pauses right before it:

  ```csharp
  new WorkflowBuilder(validate)
      .AddEdge(validate, policy)
      .AddEdge<RemediationPlan>(policy, approval, plan => plan is { RequiresApproval: true })
      .AddEdge<RemediationPlan>(policy, execute, plan => plan is not { RequiresApproval: true })
      .AddEdge(approval, execute)
      .AddEdge(execute, verify)
      .AddEdge<RemediationVerification>(verify, workItem, found => found is { RequiresWorkItem: true })
      .AddEdge<RemediationVerification>(verify, complete, found => found is not { RequiresWorkItem: true })
      .AddEdge(workItem, complete)
      .WithOutputFrom(complete)
      .Build();
  ```

  It runs through `InProcessExecution.RunStreamingAsync`, and the event stream
  (`ExecutorInvoked/Completed/Failed`, `WorkflowOutputEvent`) becomes a live step timeline.
- **Effective target, not raw schedule** — policy and verification both ask
  `LightingTarget.Resolve(expectedScheduledState, operationContext)`, the same canonical rule the
  Energy Hub commands against. A lamp deliberately lit for a security operation is **not** an
  anomaly, so the workflow never "corrects" it.
- **The command is bound to the state it was decided on** — validate captures the Energy Hub's
  `StateRevision`; the restore carries it; the Hub refuses a stale command atomically with a 409
  carrying a machine-readable `preconditionFailed` marker, so a refusal is never mistaken for a
  downstream failure. The execute step then re-validates **once** and **fails closed**: if the
  fresh state still requires approval, the earlier answer does not carry over — the twin cannot
  tell "the override the operator saw" from "a new one asserted since", so a fresh approval is
  required. Only a state that no longer needs approval is retried, against the new revision.
- **Downstream failures stay data, not crashes** — an unreachable Energy Hub or an unverifiable
  read becomes a failed correction that flows on to the work-item branch, instead of killing the
  run and quietly skipping the maintenance ticket. Run cancellation still propagates.
- **The capability can be withdrawn mid-run** — the stage is rechecked immediately before the
  command, and a downgrade below Workflow cancels every run still in flight.
- **Failure branch** — an attempted correction that does not resolve raises a maintenance work
  item in the work-management emulator (`IWorkItemGateway`). An operator's refusal is a decision,
  not a fault, and raises none.
- **Audited completion** — the terminal outcome separates `CommandExecuted` ("something changed")
  from `Resolved` ("the city is correct"), because a command can run and still leave the asset
  wrong.
- **Definition endpoint** — `GET /api/operations-agent/remediation/definition` returns the Mermaid
  diagram generated by `WorkflowVisualizer.ToMermaidString` from the executing graph plus the
  equivalent declarative YAML (`workflows/restore-remediation.yaml`), displayed, not executed. A
  deterministic test compares the YAML against the real graph's **topology** — start node, node
  set, edge endpoints, and which edges are conditional. The SDK exposes no predicate text, so the
  condition expressions written in the YAML are documentation and are not machine-checked.
- **Command Center panel** — a **Run remediation workflow** button, a live step timeline, the
  reused approval prompt, and a definition card with **Graph (generated)** / **Declarative YAML**
  tabs. The diagram mirrors the run: the active node pulses amber, finished nodes take their
  semantic outcome (green resolved, red declined/unresolved/failed, grey-dashed skipped). Mermaid
  is vendored locally; nothing loads from a CDN on stage.

## Lecture beat

1. At the Workflow stage, open the definition card: the diagram was generated *from the code that
   runs* — point at the two policy branches and the work-item branch.
2. Arm `WORKFLOW` in DemoControl, click **Run remediation workflow**: the debugger lands at the
   builder; step the slide-shaped graph construction, then continue.
3. The timeline fills node by node and the diagram lights up with it. At `approval` the run
   pauses — the same operator prompt as the MRTR stage, now raised by an orchestration node
   instead of a paused tool. **Deny** first: the gate turns red (Declined), execute goes
   grey-dashed (Skipped), verify turns red (Unresolved). A refusal never paints green, and no
   work item is raised — nothing broke; a human said no.
4. Run again, **approve**: execute restores through the Energy Hub, verify re-reads and confirms,
   the outcome badge reads SUCCEEDED, the map updates.
5. Ask the agent to restore instead: it calls `start_restore_lighting_operation`, not the write.
   The Command Center finds the run the agent started (by the ask's correlation) and follows it in
   the same panel, so its approval gate is answerable there. The agent recommends; the workflow
   decides and acts.
6. Optional, and the strongest point: apply **Security Operation** and run the workflow. Nothing
   happens — required lighting is not an anomaly. Judging against the raw schedule would have
   switched the lights off under an active operation.
7. Contrast: MRTR was a *tool* pausing mid-call; the workflow is *structure* — the pause is a node
   you can see in the diagram. Same human, different control point. Declarative YAML + Foundry
   hosting arrive in the Hosting stage.

## Verification

- Deterministic tests drive the real graph through the real engine with only the Energy Hub
  gateways faked: approve resolves, deny leaves state untouched with no work item, no-override
  anomalies skip the gate, in-schedule state is a no-op, **required security lighting is never
  remediated**, an override appearing after an automatic decision is **not** cleared without
  approval, an approval does **not** carry over to a state that still needs one, harmless
  movement retries once against the fresh revision, a stage downgrade withdraws the command, and
  a failed command, an ineffective command, an unreachable hub, and an unverifiable read each
  raise a work item. The declarative YAML is checked against the executing graph's topology.
- The state-precondition contract is proven over real HTTP: an integration test drives the actual
  Energy Hub endpoint with the real `HttpEnergyCommandGateway`, so the marker that distinguishes
  a refused precondition from a downstream failure cannot silently go missing.
- The full flow is verified live against the running stack, including the security-operation
  scenario and the agent-started run.

## Deferred (with trigger)

- **Checkpoint / resume** (requirement 9, "where practical"): runs are in-process and bounded by a
  five-minute budget, and the presenter restarts nothing mid-demo, so no `CheckpointManager` is
  wired. Trigger: a lecture beat that survives a service restart mid-approval, or a run that must
  outlive the process — then use `InProcessExecution.ResumeStreamingAsync` with a checkpoint
  manager and persist the run store.
