# Segment 13 — Agent 365: the estate has a governor

The W20 enterprise-governance segment (requirements §23, runbook §38 steps 3–5). Not a `DemoStage`:
nothing in the Aspire composition changes. The surfaces are a terminal, the directory, and — where
the tenant cooperates — the Agent 365 admin experience.

**Status: verified against the live tenant, 2026-09-05,** except the admin-portal walk itself,
which sits behind an interactive sign-in and must be verified in rehearsal.

## What this segment claims, and what it must not

Agent 365 is **estate governance**: who exists, who answers for them, what they did. It is NOT a
replacement for anything the earlier stages built, and §23 requires saying so: domain
authorization (the Energy Hub's boundary), human-in-the-loop (MRTR, gates, tool approval), the
runtime workflow, and runtime policy all stay exactly where they are. Agent 365 governs the
*population*; the stages govern the *run*.

## Verified facts the beats stand on

Probed live with `./scripts/Test-Agent365Readiness.ps1` (read-only, re-run any time):

- **The directory has a noun for this now.** The hosted agent's service principal comes back from
  Microsoft Graph as `@odata.type: #microsoft.graph.agentIdentity`, `servicePrincipalType:
  ServiceIdentity` — an *agent identity*, distinct from apps and managed identities, carrying tags
  for its region, project and agent GUID. The W20 identity-triad claim (operator ≠ agent ≠
  service) is a fact the directory states itself.
- **The owner is the pipeline.** The platform mints the identity when the first version is
  created, so its owner is whoever ran that creation — here, `caesarea-github-deploy-dev`, the CI
  principal. An unattended pipeline as the only party answering for an agent is the governance
  anti-pattern in the flesh.
- **The estate is real.** Enumerating `servicePrincipalType eq 'ServiceIdentity'` returns ten
  agent identities in this tenant — Caesarea's next to months-old experiments nobody remembers
  deploying. That list *is* the argument for estate governance.
- **Licensing is in place.** One `MICROSOFT_AGENT_365_TIER_3` seat assigned; with none, Agent 365
  does not fail loudly — telemetry is quietly dropped (see deployment.md Step 5).
- One probe found **no `agentIdentities` Graph collection** at beta (recorded as one probe, not a
  survey — the earlier toolbox lesson applies).

## The beats

1. **The identity, from the directory's own mouth** *(terminal)*. Run
   `./scripts/Test-Agent365Readiness.ps1`. Point at `#microsoft.graph.agentIdentity`: *"I did not
   register this identity. The platform minted it when the agent's first version was created, and
   the directory knows it is an agent — not an app, not a service account."*
2. **The anti-pattern** *(same output)*. Owners: one entry, and it is the deployment pipeline.
   *"Who answers for this agent? Today: a YAML file. That is what unmanaged agent estates look
   like."*
3. **The fix, live** *(terminal)*. `./scripts/Set-AgentOwner.ps1` — additive (the pipeline keeps
   deploying), idempotent, defaults to the signed-in presenter. Re-run the readiness gate: the
   human owner appears. *"The pipeline creates agents; a person answers for them."* Needs an
   application-administration role — activate via PIM before the talk, or perform it in rehearsal
   and show the `[exists]` re-run instead.
4. **The estate** *(same output)*. The ten-identity inventory, dates included. *"Four months of
   experiments, still holding identities. Multiply by every team in your organization — that is
   why the registry exists."*
5. **The registry** *(portal, or fallback)*. The Agent 365 admin experience showing the agent:
   owner, inventory, activity. **Verify in rehearsal**; capture screenshots from this same tenant
   the moment it works, store them under `docs/prompts/assets/agent365/`, and present them with
   the required label **`CAPTURED / NOT LIVE`** whenever the live portal is not used. No
   lecture-critical path may depend on this beat (§23) — beats 1–4 carry the segment on their own.
