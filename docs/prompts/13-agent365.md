## What this segment claims, and what it must not

Agent 365 is **estate governance**: who exists, who answers for them, what they did. It is NOT a
replacement for anything the earlier stages built, and §23 requires saying so: domain
authorization (the Energy Hub's boundary), human-in-the-loop (MRTR, gates, tool approval), the
runtime workflow, and runtime policy all stay exactly where they are. Agent 365 governs the
*population*; the stages govern the *run*.

## Publishing to Teams / Copilot — probed, not yet achieved

The registry's Users tab (Installed for / Available to / Shared with) and the Publisher/Channel
fields describe the distribution of a **published** agent; ours is `publish_approval_status:
not_published`, so they are empty by definition, not misconfiguration. What a personal
("just me") Teams/Copilot presence would take, per the probes of 2026-09-05:

- **The container cannot serve the Activity protocol today.** The pinned hosting family
  (`Microsoft.Agents.AI.Foundry.Hosting` 1.20 / `Azure.AI.AgentServer.*`) exposes no Activity
  mapper - a string-scan of the shipped assemblies finds none - so a container-served Activity
  endpoint waits on the SDK.
- **The platform accepts the declaration anyway.** `PATCH agent_endpoint.protocols =
  ["responses","activity"]` returns 200 and `protocol_configuration.activity: {}` appears -
  and the Responses endpoint keeps serving. Left in place. Remember the A2A lesson before
  celebrating: this API also accepted `bogus` once, so acceptance alone proves nothing; but A2A
  also taught that the platform can FRONT a protocol the container never serves, so a
  platform-bridged Activity is plausible.
- **No publish call lives on the obvious data-plane routes** - `endpoint/publish`, `publish`, and
  `endpoint/publications` all 404 at api-version v1 (three probes, recorded as three probes).
  The publish flow most likely lives in the Foundry portal's own UX, with the approval landing in
  the M365 admin center (which is what `publish_approval_status` and the registry's
  "approval" language imply).

**Corrected 2026-09-05 — a Foundry-hosted MAF agent needs NO M365 Agents SDK code to reach Teams.**
An earlier draft here concluded that publishing required a Bot Framework messaging endpoint, from
scanning the standalone `a365` DevTools CLI (whose `publish` builds a custom-engine-agent Teams
package with a `bots.messagingEndpoint`). That is one route — the standalone-bot route — and it is
the wrong one for this agent. Foundry's OWN route fronts the **Activity (Teams/M365) protocol** the
same way it fronts A2A: the container serves only Responses, and the platform translates the
channel's Activity traffic into Responses invocations. The endpoint already declares it —
`agent_endpoint.protocols: [activity, responses]`, `protocol_configuration.activity: {}`, set by a
PATCH, Responses unaffected. (Per the A2A lesson, declaration-accepted is not proof-it-works; the
portal publish is what proves it.)

The publish + add-channel action lives in the **Foundry portal**, not a v1 data-plane route
(`agents/{name}/channels`, `.../publications` and siblings all 404). So this beat is portal-driven
and needs the presenter's interactive sign-in:

1. Foundry portal → the project → Agents → **caesarea-operations** → **Channels** (or Publish).
2. Add the **Microsoft Teams / M365** channel. The platform provides the Activity bridge; no
   messaging endpoint of ours is entered.
3. **Publish**; approve in the M365 admin center if `publish_approval_status` requires it (it reads
   `not_published` until then).
4. Scope availability to the presenter (and a second user for the sharing beat) — this is where the
   registry's Users tab (Installed for / Available to) finally populates.

The agent then appears in Teams **as itself**, no relay and no person in the loop — which is the
recommended option, and the reason `Start-TeamsOperatorRelay.ps1` is explicitly the interim bridge,
not the demo's endpoint. Verify the whole path in rehearsal and capture it for the CAPTURED / NOT
LIVE fallback.

### Making the Teams channel repeatable (IaC), not a lost portal click

The repo's rule is that nothing survives only as a portal click. The agent data plane exposes no
channel/publish route (surveyed across api-versions v1 / 2025-05-15-preview / 2025-11-15-preview —
all 404), so the channel-add is portal-driven *today* — but "portal-only" was wrong here before
(the Work IQ connection's decisive field came from diffing a portal-made connection against an
API-made one). Same method, now tooled:

1. **The scriptable half is done and committed.** `./scripts/Set-AgentActivityProtocol.ps1`
   declares `activity` on the endpoint (idempotent, verifies Responses survives). This is the one
   part confirmed on the data plane.
2. **Reverse-engineer the rest.** `./scripts/Capture-AgentChannelState.ps1 -Label before`, then add
   the Teams/M365 channel and publish in the portal, then `-Label after`. Each snapshot records the
   resource group's ARM resources, any Azure Bot services and channels, and the full agent record.
3. **Diff → codify.** The strong hypothesis: the channel is backed by a
   `Microsoft.BotService/botServices` + a Teams `botServices/channels` resource whose messaging
   endpoint is the agent's Activity endpoint and whose app ID is the agent identity — all Bicep-able
   — plus a couple of flipped agent fields (`publish_approval_status`, `protocol_configuration.
   activity`) that a data-plane PATCH sets. The baseline capture confirms the starting point: **0
   bot services** in the group, so anything that appears after is the channel's footprint.

Once the diff is in hand, the Teams channel becomes `infra/` Bicep run by a workflow, exactly like
the rest of the platform — delete the agent and rebuild, and Teams comes back with it.

**Done — captured, and it is an Azure Bot (2026-09-05).** Publishing "Direct publish / Just you"
created, in `rg-caesarea-dev`:

- a `Microsoft.BotService/botServices` (`caesarea-operations71224`, kind `azurebot`, SKU S1, global)
  whose **messaging endpoint is the agent's own Activity endpoint**
  (`.../agents/caesarea-operations/endpoint/protocols/activityprotocol?api-version=2025-11-15-preview`)
  and whose **`msaAppId` is the agent's identity** (single-tenant, no stored secret — the per-agent
  identity is the bot's credential);
- an enabled **MsTeamsChannel** on it (WebChat and DirectLine come by default);
- and a data-plane change: the agent's `publish_approval_status` flipped `not_published` →
  `no_approval_needed`.

Codified as **`infra/modules/teams-channel.bicep`**, deployed by
**`./scripts/Publish-AgentToTeams.ps1`** (which reads the identity and endpoint back from the
deployed agent), and the **Activity protocol is now declared by `deploy-hosted-agent.yml`** on every
release — so a rebuilt-from-nothing agent is Teams-ready with no manual PATCH.

**The published agent was silent until Activity was declared at BOTH levels (2026-09-05).** The bot
delivered Teams/Copilot messages to the endpoint — it returned `202 Accepted` to a real Activity
envelope — but the agent never ran: no trace, and Copilot showed "still processing… try again". The
A2A precedent was the fix. A2A needed its protocol on the version's `protocol_versions` AND the
endpoint's `protocols`; Activity is the same, and only the endpoint half had been set. The version
(created by the workflow) declared `responses 2.0.0` alone. Adding `{protocol: "activity", version:
"1.0.0"}` to a new version's `protocol_versions` — accepted first try, version stayed active, and
Responses kept serving — is what routes an inbound Activity to an agent run. The workflow now emits
both on every version, so this cannot regress on redeploy. The lesson, again: a protocol accepted
on the endpoint is not a protocol the agent will serve until the *version* declares it too.

**The remaining edge, and it is an identity one (2026-09-05).** With inbound routing fixed, a
Copilot/Teams message now produces a trace — the agent runs — but the run carries three errors and
Copilot shows no reply. App Insights names them: the **Work IQ toolbox MCP call fails**
(`POST /toolboxes/caesarea-workiq/mcp` → 400, `GET` → 405, an unhandled `McpProtocolException`),
and that exception kills the turn before a clean reply is produced. The cause is the same delegation
fact this repo recorded during the hosted-agent spike: Work IQ needs the caller's **per-user
delegated identity, available only on a user request's egress**. The Command Center's Responses
path carries that identity (which is why its consent flow works); the **bot/Activity channel does
not** — the caller reaching the container over the Teams channel is the bot/agent, so Work IQ has no
user token to exchange. This is not a misconfiguration; it is where per-user OBO and a bot channel
genuinely meet their limit today.

Consequences for the demo, stated honestly:

- The Teams/Copilot-published agent handles what needs **no user delegation** — the Energy Hub
  live-state tool ("is L-417 on?") — cleanly. The **Work IQ records** beat belongs in the Command
  Center, where the user's identity flows and consent works. That division is not a workaround; it
  is the boundary the architecture already teaches.
- A Teams-facing composition **without** the Work IQ toolbox (`WORKIQ_TOOLBOX` unset) would answer
  in Teams without the turn-killing exception — at the cost of forking the composition, which the
  requirements warn against. A spike, not the default.
- Everything else of the native path works and is repeatable: publish, registry governance,
  inbound routing, and the bot/channel IaC. The one gap is Work-IQ-over-a-bot-channel, and it is a
  real platform limitation worth naming on stage rather than hiding. Two honest limits:
the Bicep creates a stably-named bot (`caesarea-operations-teams`) rather than reconciling the
portal's random-suffixed one, and the **M365 Copilot agent-store registration** the portal also
performed (the "Just you" store entry) has no confirmed ARM/data-plane route — it stays a one-time
portal step, captured for the CAPTURED / NOT LIVE fallback.

### Demonstrable today: the Teams relay

Until the native publish lands, `./scripts/Start-TeamsOperatorRelay.ps1` puts the agent in a Teams
channel the honest way: a presenter-run relay that watches for new top-level messages, forwards
each to the hosted agent, and replies in-thread — every reply labeled *"Caesarea Operations Agent
(hosted on Microsoft Foundry) · relayed as \<presenter\>"*. Graph access goes through
Connect-MgGraph: the first run prompts once for consent (`ChannelMessage.Read.All` is
admin-restricted, so an admin approves it), and the machine's token cache makes later runs silent.
A finding worth keeping: the Azure CLI **cannot** be used for this — Microsoft first-party apps'
Graph scopes are fixed by preauthorization, and an admin grant earns `AADSTS65002`, discovered by
trying exactly that.

The relay's identity boundary is itself the teaching beat: the relay runs as whoever signed in to
Graph, so a question typed by ANYONE in the channel is asked of the agent as that person, and Work
IQ evidence comes from that person's OneDrive whoever asked. A colleague in the channel proves it
live — their question, the relay runner's evidence.

The channel face can be its own identity: `./scripts/New-CaesareaOperator.ps1` mints a **Caesarea
Operator** user, licensed from the Agent 365 seats the tenant already owns — the Tier 3 seat
carries `TEAMS1`, a mailbox, OneDrive and the agent-governance service plans, i.e. it IS the
workspace licence for an agent teammate — adds it to the demo team, and pre-consents the relay's
Graph scopes for it alone. Run the relay signed in to Graph as the operator (az stays the
presenter, so the hosted call keeps the presenter's identity — the split is the demo) and the
thread speaks with the operator's face. Name the ladder on stage: *relay as me → licensed
hand-made operator → the Agent 365 AI Teammate flow (`a365 setup --aiteammate`), where the
platform mints the user-shaped identity FOR the agent and governs it.* Each rung exists because
the one below it is honest about what it fakes.

"Created by: —" is not a gap to fix: the agent WAS created by the CI pipeline, the registry
declines to render a service principal as a person, and creation is an audit fact rather than a
setting. The accountable-person field is Owner - which is the whole reason the ownership beat
exists.
